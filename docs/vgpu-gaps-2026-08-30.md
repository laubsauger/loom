# vgpu 0.3.1 — gaps found building Shaderloom on it

One note, sent once (per the orchestrator's standing list), for the vgpu maintainers.
Each entry: what is missing, how it bit us, what we do instead, and what we would
delete the day it lands. Ordered by how much silent damage the gap can do.

## 1. `gpu.onError` never forwards the device's uncaptured-error path

`onError` carries vgpu's own scoped errors only. A verdict outside any scope — a
bind-group or dispatch-time validation failure — lands on the raw device's
`uncapturederror` with nobody listening.

**How it bit:** a compute pipeline binding 9 storage buffers against a granted 8
compiled, "rendered" every frame, and reported nothing anywhere (our B33). The
pipeline is built lazily, so the failure surfaced at first dispatch — after any
compile-scoped listener has unsubscribed — and went to the unheard path.

**Workaround:** we attach `onuncapturederror` on the raw device for the session's
lifetime and route it into our diagnostics hub (T327). Delete-on-fix: that reach-through.

**Ask:** forward uncaptured errors to `onError` (flagged as unscoped), or expose a
`onUncapturedError` beside it.

## 2. `compute.dispatch()` self-submits — no frame-level compute pass

Each dispatch builds and submits its own command buffer immediately, while draws
encode into the open frame and submit at frame end.

**How it bit:** an effect→dispatch chain within one frame ran the dispatch BEFORE the
effect it reads from (our B19): the dispatch sampled last frame's texture — or zeros —
with no error and a plausible picture.

**Workaround:** on the direct path we segment encoding at every dispatch boundary and
submit segments in plan order (`encodeSegmented`); on the loop path we document a
1-frame effect→dispatch latency. Ring rotation (below) inherited the same dance.

**Ask:** `frame.compute(...)` — a compute pass recorded into the frame's encoder, so
plan order is execution order.

## 3. No `timestampWrites` on compute passes

**How it bit:** per-pass GPU timings (our T163 profiler) cover draws only; kernels —
often the expensive half of a particle graph — are invisible in the timing panel.

**Ask:** accept the timestamp-query pair on compute passes the way draw passes do.

## 4. `target()` cannot wrap an existing texture or a layer view

`target()` always allocates and owns its texture; there is no way to render into a
caller-provided `GPUTexture` layer or view.

**How it bit:** per-pixel time displacement (our T321) needs frame history as ONE
`texture_2d_array`. Since producers can only render into `target()`s, we keep an
ordinary write target and `copyTextureToTexture` into the array layer each frame —
one full-frame copy per ring per frame that direct layer rendering would delete.

**Ask:** `target({ texture, baseArrayLayer })` adoption, mirroring `initFromDevice`'s
philosophy at the resource level.

## 5. `Effect` has no `destroy()`

Effects hold pipelines and bind-group references with no explicit release; disposal
rides the device teardown.

**How it bit:** structural recompiles that replace effects (our per-entry carry-over
diffing) can only drop references and trust GC; on long editing sessions the pipeline
count only grows until device teardown.

**Ask:** `effect.destroy()`, idempotent, like every other resource.

## 6. Standalone `draw()` lacks clear and timer hooks

Outside a frame, a draw cannot clear its target first and cannot carry a timestamp
pair.

**How it bit:** indirect draws (GPU-driven instance counts, our T322) always clear —
"accumulate" trails are silently impossible on that path — and are invisible to the
profiler. Documented as a gap in our plan reader rather than worked around.

**Ask:** `draw({ clear, timer })` parity with the frame path.
